Redes, Logs y Privacidad IP

Guía técnica sobre el modelo cliente-servidor en HTTP, la configuración de access logs en Nginx/Apache y los mecanismos que afectan a la visibilidad de una dirección IP.

1. Cliente-Servidor HTTP 2. Access Logs 3. Privacidad IP

1. Modelo cliente-servidor en HTTP

HTTP (HyperText Transfer Protocol) es un protocolo de la capa de aplicación basado en un modelo petición-respuesta. Un cliente (normalmente un navegador) envía una petición a un servidor, y el servidor devuelve una respuesta.

Flujo de una petición HTTP

CLIENTE SERVIDOR (navegador) (nginx, apache) | | | 1. Resolución DNS: ejemplo.com -> 93.184.216.34| |------------------------------------------------>| | | | 2. Conexión TCP (3-way handshake) | | SYN -------------------------------------->| | <------------------------------------ SYN-ACK| | ACK -------------------------------------->| | | | 3. (Si HTTPS) Handshake TLS | | ClientHello ------------------------------->| | <------------------------------- ServerHello| | <------------------------------- Certificado| | ... intercambio de claves ... | | | | 4. Petición HTTP | | GET /index.html HTTP/1.1 ----------------->| | Host: ejemplo.com | | User-Agent: Mozilla/5.0 | | Accept: text/html | | | | 5. Respuesta HTTP | | <---------------- HTTP/1.1 200 OK | | <---------------- Content-Type: text/html | | <---------------- Content-Length: 1256 | | <---------------- <html>...</html> | | | | 6. Cierre de conexión (o keep-alive) |

Estructura de un paquete HTTP

Una petición HTTP consta de:

  • Línea de petición: método (GET, POST, etc.), ruta (/index.html) y versión (HTTP/1.1).
  • Cabeceras (headers): metadatos como Host, User-Agent, Accept, Cookie, Authorization.
  • Cuerpo (body): opcional, usado en POST y PUT para enviar datos.

¿Dónde viaja la IP en TCP/IP?

HTTP va montado sobre TCP, que a su vez va sobre IP. La dirección IP viaja en la cabecera del paquete IP, en dos campos:

CapaProtocoloQué añadeDónde está la IP
AplicaciónHTTPMétodo, headers, bodyNo hay IP aquí
TransporteTCPPuertos origen/destino, flags, secuenciaNo hay IP aquí
RedIPIP origen, IP destino, TTLAquí sí
EnlaceEthernet/WiFiMAC origen, MAC destinoNo hay IP aquí

El paquete IP tiene esta forma:

+--------+--------+--------+--------+
| Version|  IHL   |    ToS         |  (1 byte + 1 byte + 1 byte)
+--------+--------+--------+--------+
|          Total Length             |
+--------+--------+--------+--------+
|         Identification            |
+--------+--------+--------+--------+
|Flags|      Fragment Offset        |
+--------+--------+--------+--------+
|   TTL  |   Protocol   |  Header   |
|        |              |  Checksum |
+--------+--------+--------+--------+
|         Source IP Address         |  <- IP del CLIENTE
+--------+--------+--------+--------+
|      Destination IP Address       |  <- IP del SERVIDOR
+--------+--------+--------+--------+
|          Options (opcional)       |
+--------+--------+--------+--------+
|              Payload              |  <- Aquí va TCP + HTTP
+--------+--------+--------+--------+

Cuando el cliente envía una petición HTTP, el paquete IP lleva la IP del cliente en el campo Source y la IP del servidor en Destination. El servidor, al recibirlo, puede ver la IP del cliente. Cuando responde, invierte los campos.

Importante: la IP del cliente es visible para el servidor en la capa IP, no en HTTP. Por eso los servidores web pueden registrar la IP en sus logs de acceso, aunque el cliente no la envíe explícitamente en ningún header HTTP.

NAT: cómo varias máquinas comparten una IP

La mayoría de redes domésticas usan NAT (Network Address Translation). Tu router tiene una IP pública asignada por tu ISP, y todos los dispositivos de tu casa (móvil, portátil, TV) comparten esa IP pública. Internamente usan IPs privadas (192.168.x.x, 10.x.x.x). El router traduce las IPs privadas a la pública al salir a internet.

[Móvil 192.168.1.10] \ [PC 192.168.1.11] >--- [Router NAT] --- [IP pública 88.12.34.56] --- Internet [TV 192.168.1.12] / | | Traduce IP privada -> pública Guarda tabla de traducciones

2. Configuración de access logs en Nginx y Apache

Los access logs registran cada petición que recibe el servidor: IP del cliente, fecha, ruta solicitada, código de respuesta, user-agent, etc. Se usan para monitorizar tráfico propio, detectar ataques, auditar accesos y depurar errores.

Nginx: directivas de access_log

En Nginx, los logs se configuran en nginx.conf o en los archivos de sitio dentro de /etc/nginx/sites-available/.

# Formato por defecto (combined)
log_format combined '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent"';

# Access log global
access_log /var/log/nginx/access.log combined;

# Access log por sitio
server {
    listen 80;
    server_name ejemplo.com;

    access_log /var/log/nginx/ejemplo.access.log combined;
    error_log  /var/log/nginx/ejemplo.error.log warn;

    location / {
        root /var/www/ejemplo;
        index index.html;
    }
}

Variables útiles en Nginx:

VariableQué contiene
$remote_addrIP del cliente (o del proxy si hay uno delante)
$http_x_forwarded_forIP original si el cliente viene detrás de un proxy
$requestLínea de petición completa (método + ruta + versión)
$statusCódigo de respuesta HTTP (200, 404, 500…)
$http_user_agentNavegador y sistema operativo del cliente
$request_timeTiempo que tardó la petición en segundos

Apache: directivas de CustomLog

En Apache, los logs se configuran en httpd.conf o en los virtual hosts.

# Formato combined (por defecto)
LogFormat "%h %l %u %t \"%r\" %>s %b \"%{Referer}i\" \"%{User-Agent}i\"" combined

# Access log global
CustomLog /var/log/apache2/access.log combined

# Virtual host
<VirtualHost *:80>
    ServerName ejemplo.com
    DocumentRoot /var/www/ejemplo

    CustomLog /var/log/apache2/ejemplo.access.log combined
    ErrorLog  /var/log/apache2/ejemplo.error.log
</VirtualHost>

Directivas útiles en Apache:

DirectivaQué hace
LogFormatDefine el formato de las líneas del log
CustomLogAsigna un archivo y formato al access log
ErrorLogArchivo donde se escriben los errores
LogLevelNivel de detalle de los errores (warn, error, debug…)
SetEnvIfCondiciones para decidir qué se registra

Privacidad de datos en los logs

Las IPs son datos personales según el GDPR. Si vas a guardar logs, debes aplicar medidas:

Obligaciones GDPR para logs:
  • Minimización: registra solo lo necesario. No guardes headers completos ni cookies si no los usas.
  • Anonimización: sustituye el último octeto de la IP por 0. Ejemplo: 88.12.34.0 en lugar de 88.12.34.56.
  • Seudonimización: guarda un hash de la IP en lugar de la IP en claro.
  • Retención limitada: borra los logs pasados X días (normalmente 30–90).
  • Acceso restringido: solo administradores deben poder leer los logs.

Anonimizar IP en Nginx

# Enmascara el último octeto de IPv4 y los últimos 80 bits de IPv6
map $remote_addr $remote_addr_anon {
    ~(?P<ip>\d+\.\d+\.\d+)\.\d+    "${ip}.0";
    ~(?P<ip>[a-f0-9:]+:+)+[a-f0-9]+ "${ip}::";
    default                          "0.0.0.0";
}

log_format privacy '$remote_addr_anon - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent';

access_log /var/log/nginx/access.log privacy;

Anonimizar IP en Apache

# Con mod_remoteip + mod_log_config
# O usando un formato personalizado con expresiones
LogFormat "%{REMOTE_ADDR}e ..." ...

# Alternativa: rotar y ofuscar con logrotate + script externo
/var/log/apache2/*.log {
    daily
    rotate 30
    compress
    delaycompress
    missingok
    notifempty
    create 640 root adm
    sharedscripts
    postrotate
        /usr/bin/systemctl reload apache2 > /dev/null
    endscript
}
Buena práctica: guarda los logs en un volumen cifrado, con permisos 640 y propietario root:adm. Si tu web tiene login, nunca registres contraseñas ni tokens en el log. Revisa el User-Agent solo cuando sea necesario para seguridad.

3. Mecanismos que afectan a la visibilidad de una IP

La IP que ve un servidor no siempre es la IP real del usuario. Varios mecanismos se interponen y modifican lo que el servidor percibe.

Proxies

Un proxy es un intermediario que recibe la petición del cliente y la reenvía al servidor. El servidor ve la IP del proxy, no la del cliente.

[Cliente 88.12.34.56] --> [Proxy 203.0.113.10] --> [Servidor] | +-- El servidor ve 203.0.113.10

Si el proxy añade la cabecera X-Forwarded-For, el servidor puede saber la IP original. Si no, la pierde.

X-Forwarded-For: 88.12.34.56, 203.0.113.10
X-Real-IP: 88.12.34.56

VPN (Virtual Private Network)

Una VPN cifra todo el tráfico del cliente y lo enruta a través de un servidor VPN. El servidor web ve la IP del servidor VPN, no la del cliente. Además, el ISP del cliente no puede ver qué sitios visita.

[Cliente] ==túnel cifrado==> [Servidor VPN 198.51.100.5] --> [Servidor web] | El servidor web ve 198.51.100.5

CGNAT (Carrier-Grade NAT)

Muchos ISPs usan CGNAT: en lugar de dar una IP pública a cada cliente, comparten una sola IP pública entre cientos o miles de clientes. Esto hace que la IP visible sea la del ISP, no la del usuario, y que la geolocalización apunte a la sede del ISP.

[Cliente A 10.0.0.1] \ [Cliente B 10.0.0.2] >-- [CGNAT del ISP] -- [IP pública 100.64.x.x] --> Internet [Cliente C 10.0.0.3] /

Con CGNAT, la IP pública compartida puede estar en otra ciudad distinta a la del usuario.

Tor

Tor enruta el tráfico a través de tres nodos voluntarios, cifrando en capas. El servidor web ve la IP del nodo de salida, no la del cliente. La geolocalización de esa IP suele ser aleatoria (el nodo puede estar en cualquier país).

Datos móviles

Cuando navegas con datos móviles (4G/5G), tu operadora te asigna una IP de su pool, compartida entre muchos usuarios. La geolocalización por IP suele apuntar a la sede de la operadora, no a tu posición real.

Por qué la geolocalización por IP nunca es exacta

  • Las bases de datos de geolocalización (MaxMind, IP2Location) asignan ubicaciones a rangos de IP, no a IPs individuales.
  • Los ISP reasignan IPs dinámicamente cada pocas horas o días.
  • Una IP puede estar registrada en una ciudad pero usarse en otra provincia.
  • Con CGNAT, miles de usuarios comparten la misma IP.
  • La precisión típica es a nivel de ciudad o provincia, y a veces ni eso.
Conclusión técnica: la IP es un identificador de red, no de persona. Su visibilidad depende de proxies, VPNs, CGNAT, Tor y el tipo de conexión. La geolocalización por IP es aproximada y no permite localizar a un usuario concreto. Para obtener la IP real de una persona solo se puede mediante orden judicial al ISP o a la plataforma correspondiente.

Cómo proteger tu propia IP

  • Usa una VPN de confianza (Mullvad, ProtonVPN, IVPN).
  • Usa Tor Browser para anonimato fuerte.
  • Revisa los permisos de tu navegador (WebRTC puede filtrar tu IP local).
  • No hagas clic en enlaces sospechosos de desconocidos.
  • Usa DNS cifrado (DoH/DoT) para evitar fugas.
  • En móvil, desactiva WebRTC en navegadores que lo permitan.
